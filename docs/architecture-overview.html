BaluHost Architektur

BaluHost ist ein selbst gehosteter Heimserver mit NAS-Kern. Diese Seite zeigt, aus welchen Prozessen er zur Laufzeit besteht, wie eine Anfrage durch die Schichten läuft und über welche Kanäle die Prozesse miteinander reden.

Fünf Units, eine Datenbank

In Produktion besteht BaluHost aus fünf systemd-Units. Gemeinsamen Arbeitsspeicher haben sie nicht: Was mehr als ein Prozess wissen muss, steht in PostgreSQL oder als JSON-Datei unter /dev/shm. Ein Klick auf einen Baustein öffnet seine Detailansicht mit Eckdaten, innerem Aufbau, Verbindungen und Code-Pfaden.

Weg einer Anfrage durch die Schichten

Beide Hälften sind gleich geschnitten: je Fachgebiet eine Datei pro Schicht. Zu api/routes/raid im Backend gehört api/raid.ts im Frontend, zum Pydantic-Schema das TypeScript-Interface. Eine Anfrage läuft in dieser Reihenfolge durch. Jede Schicht lässt sich für Details öffnen.

Browser

client/src/
  1. 1Seite hinter einer Route, lazy geladen. Setzt Komponenten aus components/ zusammen und enthält kaum eigene Logik.
  2. 2Datenhaltung mit TanStack Query: useQuery mit Polling, useMutation mit Invalidierung. Schlüssel kommen aus lib/queryKeys.ts.
  3. 3Eine typisierte Funktion je Endpunkt, ein Modul je Fachgebiet. Kein Cache, keine Fehlerbehandlung.
  4. 4Die eine axios-Instanz. Hängt das Token an und meldet ein 401 als auth:expired an den AuthContext.
HTTPS/api/…Bearer-JWT

Server

backend/app/
  1. 5Beendet TLS, begrenzt die Rate (api_limit, auth_limit) und reicht an einen der vier Worker weiter.
  2. 6Neun Schichten um jede Anfrage: Security-Header, Kanal-Markierung, Plugin-Gate, Auto-Wake aus dem Sleep, Geräte-Tracking, Fehlerzähler.
  3. 7Nur HTTP-Belange: Auth-Dependency, Rate-Limit-Dekorator, Validierung über ein Schema aus schemas/.
  4. 8Die Fachlogik. Hardware-Services wählen hier ihr Backend: Simulation im Dev-Modus, echte Befehle in Produktion.
  5. 9SQLAlchemy-2-Modelle auf PostgreSQL. Schemaänderungen laufen über Alembic-Migrationen.

Quer durch das Frontend

  • contexts/: Provider in fester Reihenfolge Auth, Version, Plugin, Notification, Upload; dazu das Theme mit sechs Farbschemata.
  • i18n/: i18next mit Deutsch und Englisch in je 22 Namespaces.
  • lib/features.ts: Build-Schalter __DEVICE_MODE__. Der Pi-Build enthält nur Login, Dashboard und Systemmonitor.
  • plugin-runtime/: eigenes Bundle, das im iframe eines Plugins startet.

Quer durch das Backend

  • core/: Konfiguration aus Umgebungsvariablen, Datenbank-Engine, JWT mit Typ-Claim, Rate-Limiter, Fehlerklassen mit client-sicherer Meldung.
  • core/lifespan.py: Start und Stopp aller Hintergrunddienste samt Wahl des Primary.
  • plugins/: Plugin-Framework, siehe unten.
  • compat/: Brücke zur WSGI-Bibliothek WsgiDAV für den WebDAV-Prozess.

Kanäle zwischen den Prozessen

Sechs API-Prozesse und drei Worker müssen sich abstimmen, ohne einander direkt aufzurufen. Jeder Kanal hat genau eine Aufgabe.

KanalSchreibtLiestWofür
Postgres LISTEN/NOTIFY
ws_bus		 jeder Prozess, auch Scheduler und Monitoring ein Listener je API-Prozess WebSocket-Nachrichten. Zustellen kann nur der Prozess, der den Socket hält, also geht jede Nachricht über den Bus an alle. Bewusst nicht dauerhaft gespeichert.
JSON-Dateien
/dev/shm/baluhost/		 Monitoring-Worker API-Worker Live-Metriken wie CPU, RAM, Disk-I/O und SMART-Zusammenfassung, ohne Datenbankabfrage je Request.
Command-Queue
power_commands		 Follower-Worker Primary Hardware-Befehle. Eine Zeile wandert von pending über running zu applied oder failed, trägt eine Frist und wird höchstens einmal ausgeführt.
Scheduler-Aufträge
scheduler_executions		 API legt Zeile mit Status requested an Scheduler-Worker fragt ab „Jetzt ausführen“ aus der Oberfläche sowie der Verlauf aller Läufe.
Zustandszeilen
sleep_runtime_state, webdav_state, scheduler_state		 der Prozess, dem der Zustand gehört alle anderen Heartbeats und Zustände, die jeder Worker beantworten können muss, etwa „schläft das System gerade“.
Plugin-Aktivierung
plugin_enablement		 der Worker, der den Schalter bedient alle Worker, mit 5-Sekunden-Cache Ein Plugin-Schalter wirkt nach wenigen Sekunden in allen Workern, ohne Neustart.

Plugins: zwei Vertrauensstufen

Plugins bringen Routen, Hintergrundaufgaben, Dashboard-Panels, Status-Pills und eigene Oberflächen mit. Mitgelieferte Plugins laufen im Host-Prozess. Fremder Code aus dem Marktplatz läuft auf beiden Seiten hinter einem schmalen Kanal: auf dem Server im Subprozess, im Browser im iframe. Die Bausteine im Bild sind anklickbar.

MitgeliefertExtern
Herkunftplugins/installed/, im Repo gepflegtMarktplatz, installiert nach /var/lib/baluhost/plugins
Läuftals Python im Host-Prozessals Subprozess unter eigenem Benutzer
RechteBerechtigungen, die der Admin beim Aktivieren bestätigtCapability-Scopes, standardmäßig alles verboten
Zugriffvolle Host-APIkein Import, keine Datenbank, kein Dateisystem, keine Shell
Beispieleaudio_control, bluetooth, display_output, optical_drive, steam_gaming, tapo_smart_plugderzeit keine ausgerollt

Der Marktplatz-Index ist die Stelle, an der fremder Code ins System kommt. Deshalb prüft MarketplaceService.get_index() eine abgesetzte ed25519-Signatur über genau die Bytes, die danach geparst werden. Fehlt der Schlüssel, die Signatur oder stimmt sie nicht, wird der Index abgelehnt. Einen unsignierten Ausweichweg gibt es nicht.

Vom Pull Request auf die Maschine

Fremder Code aus einem Pull Request und der Produktions-Deploy laufen auf getrennten Runnern mit getrennten Rechten. Beide Schritte warten auf eine Freigabe von Hand.

  1. Pull Requestci-check.yml baut das Frontend und fährt die Backend-Tests, auf dem Sandbox-Runner in rootless Podman.
  2. Merge nach mainVon Hand durch den Maintainer, sobald die Checks grün sind.
  3. Freigabedeploy-production.yml hält im Environment production an, bis der Lauf bestätigt ist.
  4. Deployci-deploy.sh auf dem Prod-Runner: Code aktualisieren, Unit-Dateien rendern, Dienste neu starten, Health-Check, sonst Rollback.
  5. Pre-Release-Tagv1.38.0-pre.n entsteht erst nach gelungenem Deploy und löst create-release.yml aus.
